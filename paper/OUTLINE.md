## The claim, in one sentence

> Behavioural provenance for agentic systems has an **irreducible explicit component** —
> the rationale for a decision is a local variable at the moment of decision, so no
> callback, span, or post-hoc query can recover it — and a small explicit instrumentation
> layer over W3C PROV captures it, at a cost we measure, for every agent in a running
> multi-agent system including the agents that govern the others.

Three defensible contributions:

- **C1 — Capture, not retrieve.** A structural argument that decision rationale is
  unreachable by external observation, supported by an A-vs-B comparison over the same
  agents. *The structural argument is written; the baseline is Phase 3.*
- **C2 — A reflexive multi-agent provenance architecture.** Operational agents emit typed
  PROV about themselves; meta agents consume *that* and emit PROV in turn. Demonstrated
  running, not proposed. *Scope: one level deep — see Limitations.*
- **C3 — The `yp:` vocabulary and the 6-step lifecycle as a reusable template**,
  instantiated by four heterogeneous agents (deterministic, LLM, hybrid) and governed
  uniformly. *The lifecycle is demonstrated; the vocabulary artifact is Phase 7.*

### E0 — Conformance *(new; the precondition for every other claim)*

Interoperability with W3C PROV is an explicit contribution, so it is judged by an
independent implementation (the reference `prov` library), not by project code.

| | before Phase 1 | after |
|---|--:|--:|
| Emitted documents accepted by the reference PROV-JSON parser | **0 of 24** | **24 of 24** |
| `yp:pid` pointers dereferenceable by a fresh process | **0 of 8** | **8 of 8** |

**Why this belongs in the paper.** A single non-standard key at the document root made a
conforming parser reject every file whole — so the interoperability claim had been
inverted, not merely weak. Stating the conformance figure, and naming the judge, is what
distinguishes a standards claim from an assertion. It also pre-empts the obvious reviewer
question about a project proposing a PROV extension.

### E2 — Instrumentation coverage, and conformance to a declared standard

Two tables that are easy to confuse, and the second is the one worth printing.

**Coverage: 24 of 24 decisions carry a justification.** This is a conformance check on the
instrumentation, not a result. The code that counts decision activities is the code that
justifies them, so no run of this system could report another number, and the figure says
nothing about whether a justification is *informative*. Report it as evidence that no
decision point was left uninstrumented, and nothing more.

**Conformance: 24 of 24 records satisfy `vocab/shapes.ttl`.** This one has an external
judge. The rule — every `yp:DecisionActivity` carries a non-empty `yp:justification`, on an
activity that is dated, ended and attributed — is declared in SHACL in the vocabulary, not
written into the agent that enforces it. It is applied by `pyshacl` over RDF converted by
the reference `prov` library. Neither the rule nor the engine is ours, which is the whole
difference between a conformance statement and a self-report.

| Shape | What it requires | Records checked |
|---|---|--:|
| `decision-justified` | a non-empty justification on every decision | 24 |
| `decision-concluded` | a verdict on every decision | 24 |
| `activity-started` · `activity-ended` · `activity-attributed` | every step dated, ended, attributed to an agent | 24 |
| `pointer-verifiable` | every `yp:pid` accompanied by a `sha256:` hash | 8 |
| `granularity-declared` · `persistence-declared` · `emitter-identified` | the record describes its own configuration | 24 |

**Declaring the standard immediately found a defect in the agent that had been enforcing
it.** MC1 tested `if not activity.get("yp:justification")`, so a justification of pure
whitespace passed; the shape's `sh:pattern "\S"` rejects it, and the evaluation harness
strips before counting. Three implementations of one rule, and the agent was the one that
disagreed. That is the argument for declaring a standard rather than implementing it:
*a rule written once in one place cannot disagree with itself.*

The shapes are also tested for teeth. Each is checked by mutating a conforming record in
the specific way that shape exists to catch — a suite that passes everything is decoration,
and this is how the whitespace gap surfaced.

### E3 — Strategy A vs Strategy B *(measured, Phase 3)*

One callback baseline (`eval/baseline.py`), the same agents, the same input, the **same
run**. Strategy A is fed the 96 `StepEvent`s a framework callback handler receives — node
name, timings, input and output payloads, errors — and reconstructs as much W3C PROV as
that stream supports. Both A columns come from that one recorded stream.

| Signal | A, zero config | A, with type map | B |
|---|--:|--:|--:|
| Documents emitted | 24 | 24 | 24 |
| Activities | 96 | 96 | 96 |
| …of them typed | 0 | 96 | 96 |
| Entities | 54 | 54 | 78 |
| …of them typed | 0 | 0 | 78 |
| …carrying a resolvable pointer (`yp:pid`) | 0 | 0 | 8 |
| `used` | 72 | 72 | 72 |
| `wasGeneratedBy` | 54 | 54 | 54 |
| `wasInformedBy` | 72 | 72 | 72 |
| `wasDerivedFrom` | 30 | 30 | 30 |
| `wasAssociatedWith` | 96 | 96 | 96 |
| **Relations, total** | 324 | 324 | 324 |
| Decisions carrying `yp:verdict` | 0 | **24** | 24 |
| Decisions carrying **`yp:justification`** | **0** | **0** | **24** |
| Accepted by the reference `prov` parser | 24 | 24 | 24 |

The last row is a concession, and it belongs in the table. The pre-Phase-3 version claimed
Strategy A produced no W3C PROV-JSON; that was the fourth of its four wrong zeros. A
callback reconstruction serialises to conformant PROV-JSON perfectly well. Syntax was never
the differentiator, and a baseline that could be dismissed on syntax would make this
comparison about serialisation rather than about what a record is able to say.

**Four claims, in the order a reviewer will test them.**

*A is an upper bound.* The event stream is built from the declarations the explicit
instrumentation made: the entity each step said it read, the entity each step said it
wrote. A real handler gets a node's whole input payload and must guess which part mattered,
so it would over-report `used` and could not separate a load-bearing input from an
incidental one. Conceding A every structural fact B declared is deliberate — it turns the
last row from a comparison between implementations into a statement about the ceiling.
**Even granted every structural fact explicit instrumentation declares, the rationale is
unreachable.**

*Structure is recoverable, and the baseline recovers all of it.* 96 activities, 324
relations, identical to B. The four zeros this table carried before Phase 3 were asserted,
and three of them were false. Saying so plainly is cheaper than having it pointed out.

*Types and identity are where the structural gap actually is.* A types nothing with no
configuration and everything with ten hand-written label patterns — so the types exist, but
as a per-system artifact someone writes and maintains, and only because these labels are
descriptive. Entities are worse: A is handed payloads rather than references, so it mints
identity from content, types none of the 54, and carries no `yp:pid` at all. The
pointers-not-payloads design has no analogue in a reconstruction that never saw where a
payload was stored.

*The verdict is often recoverable; the reasoning never is.* A recovers 24 of 24 verdicts —
honestly reported, and reported as fragile: it recovers them by scraping a developer-chosen
label, and a graph whose decision node is named `decide` yields none. The justifications are
recoverable under no labelling convention at all. Searching everything the handler could
read — 222 strings, 12,425 characters — finds 0 of 24. Each justification is prose composed
at the moment of decision out of evidence the step never returned: a local variable, and the
callback layer is outside the function.

**This is the single earned zero.** It isolates exactly what explicit instrumentation buys,
and it is worth more than the four unearned ones it replaces. §7's worked example (CA1's
ESCALATE) is the qualitative companion: no callback could produce that sentence, because the
sentence is assembled from a quorum set and an integrity result that the step reported
nowhere but into the record.

### E4 — Reflexivity

All four operational agents are governed by both meta agents, and the meta agents emit
their own typed PROV, which is visible in the artifact names
(`…__cax_prov.json` → `…__cax__mc1_prov.json`).

**Stronger result now available: self-application.** MC1 enforces that every agent record a
justified decision activity. Applying MC1 to MC1's own output is a one-line experiment, and
it previously failed — the checker could not satisfy its own rule. It now passes, as does
MC1 applied to MC3. That is a sharper statement of reflexivity than a governance table, and
it is a test in the suite rather than a claim in prose.

**The depth, and why it is a property rather than a gap.** `governance.*` is terminal:
nothing consumes it, so reflexivity in a run is one level deep. That bound is deliberate.
An agent that governs governance output emits a record that is itself governance output,
and nothing in the subject structure stops the next pass — publishing to a prefix nobody
subscribes to makes the recursion impossible by construction, which is worth more than a
depth counter someone can forget to check.

So contribution C2 carries the qualifier, and the bound is a tested invariant rather than a
documented defect: `test_governance_output_is_terminal_by_design` fails if any agent starts
consuming `governance.*` without a bounded depth scheme arriving alongside it. A bounded
second level, with the depth carried in the subject, is named as future work and not
claimed.

### E5 — Verdicts, and their reachability *(complete)*

| Agent:verdict | Count in the reference run |
|---|--:|
| `ca1:ACCEPT` | 2 |
| `ca2:REVISE` | 2 |
| `ca3:ANOMALY` | 2 |
| `cax:ACCEPT` | 2 |
| `mc1:PASS` | 8 |
| `mc3:COMPLETE` | 8 |

The tally is the less interesting half. A verdict that only ever takes one value carries no
information, so what has to be established is that the alternatives are *reachable* — and
the ordinary run reaches six of twelve. The other six come from seven injected faults
(`eval/fault_injection.py`, archived under `experiments/verdict-reachability`):

| Verdict | How it was provoked | Observed |
|---|---|:--:|
| `ca1:ESCALATE` *(integrity)* | a store that writes bytes it did not hash | ✅ |
| `ca1:ESCALATE` *(consumption-unconfirmed)* | no consumer acknowledged before the timeout | ✅ |
| `mc1:FAIL` | a third-party record whose decision carries no justification | ✅ |
| `mc3:PARTIAL` | a third-party record with an activity started and never closed | ✅ |
| `ca2:ACCEPT` | a producer record that actually carries measurements | ✅ |
| `cax:REVISE` | a scripted model reply naming figures absent from the graph | ✅ |
| `ca3:OK` | a fully instrumented graph with regular timing | ✅ |

**Twelve of twelve verdicts observed.** Three things in that table are worth a sentence each
in the text.

*The two escalation paths are distinguishable in the record, and they demand opposite
responses.* `yp:escalation_reason` separates `integrity` from `consumption-unconfirmed`: the
first says the stored bytes are wrong, the second says the data is fine and a consumer is
down. The justifications differ accordingly — one quotes both hashes of the mismatch, the
other names the three consumers that never answered and states that the
persist-after-consume ordering was forfeited. An operator handed only "ESCALATE" learns
nothing actionable, which is the whole argument for the field.

*Three of the seven are not failures at all.* CA2's ACCEPT, CAx's REVISE and CA3's OK are
unreachable from the bundled sample data — the real yProv4ML records carry no numeric
`prov:value` entities to plot, and declare start times without end times. So "CA2 always
says REVISE" was a finding about the *input*, not about CA2, and separating those two is
what these scenarios are for. It also sharpens CA3's result: ANOMALY is informative
precisely because OK is reachable.

*`mc1:FAIL` is unreachable from records this library produces.* `ProvTracker.decide()`
refuses a blank justification at the call site, so an agent instrumented with this library
cannot emit an unjustified decision. FAIL is reachable for records the library did not
write — which is the case a compliance checker exists for, since it is pointed at agents
you do not control. That is a property worth claiming rather than a gap to apologise for:
**the instrumentation makes the violation unrepresentable, and the governance layer catches
it in input that was not instrumented.**

Every fault is injected into the input or the environment, never into the check being
tested, and `tests/test_fault_injection.py` enforces all seven plus the matrix itself — so
a verdict advertised in the README and never observed fails the build.

### E5b — Model provenance: can an LLM step be repeated from the record? *(measured, Phase 4)*

Before Phase 4, no. The emitted graph named no model, no sampling parameters, no prompt and
no token counts, so the one step in the pipeline that was not deterministic was the one step
the record could not account for (review findings F1, F2). For a paper about *agentic AI*
provenance that was the most substantive gap in the artifact.

`experiments/phase4-llm` is a gpt-4o run with `LLM_REQUIRED=1`. Every model-bearing step now
carries:

| Attribute | Example | Why the record needs it |
|---|---|---|
| `yp:model` | `gpt-4o` | the call cannot be repeated without it |
| `yp:temperature` · `yp:max_tokens` | `0.2` · `400` | the output distribution is a function of these |
| `yp:prompt_id` · `yp:prompt_version` · `yp:prompt_sha` | `act.system` · `2.0` · `3f831826f610` | a prompt is apparatus; the hash catches a forgotten version bump |
| `yp:prompt_tokens` · `yp:completion_tokens` | `226` · `107` | cost, and how much context actually reached the model |
| `yp:llm_latency_s` | `5.043` | separates model time from instrumentation time in E6 |
| `yp:finish_reason` · `yp:response_sha` | `stop` · `eaae9be93d4d` | whether it finished, and over which exact bytes |

Four model calls across the run: 2,071 prompt tokens, 473 completion tokens.

Three details worth a sentence each in the text.

*The prompt registry was already there and nothing imported it.* `prompts.py` is 238 lines
with versions, changelogs and content hashes, written for exactly this; both LLM agents
built their prompts as inline f-strings instead. The fix is not new infrastructure, it is
making the call site go through the registry — `runtime/llm.py` takes a `Prompt`, not a
string, so a prompt cannot reach a model without its identity reaching the record.

*An absence is recorded as an absence.* The computed fallback path stamps no model
attributes at all, rather than zeros or `"none"`. A zero token count is a measurement, and
on that path no measurement was made.

*The response hash and the entity pointer agree, and may legitimately disagree.*
`yp:response_sha` on the activity and the `yp:pid` of the generated entity are both content
hashes of the model's text, so they match here. They are attached to different claims — one
says what the call returned, the other says what was stored — and an agent that
post-processes model output before storing it would make them differ. That divergence is
informative, which is why both are recorded.

### E5c — A negative result: energy cannot be attributed per agent step *(Phase 4)*

`energy.py` was 311 lines that nothing called, while CA3 reported "no energy or emission
streams" as a completeness gap in the graphs it analysed — and was right about the agents
that emitted it (finding F3). Phase 4 wired it into the capture API: every step closed
through the API carries the energy attributable to it, opt-in via `PROV_ENERGY`.

Wiring it produced a result worth reporting on its own terms. **A sampling backend cannot
attribute energy to a step shorter than its sampling period.** codecarbon's default period
is 15 seconds; these steps last milliseconds, so a delta lands on whichever step happens to
read after a tick:

| step | energy | step duration |
|---|--:|--:|
| choose what to plot | 46.9 µWh | 0.000 s |
| render chart (matplotlib) | 4.6 µWh | 1.328 s |

The step that did the work was charged a tenth of what the step that did nothing was
charged. A second artifact was worse: the *first* step of each record was charged 28.3
seconds of inter-message idle time, because the energy tracker outlives any one record.

Both are now handled, and the handling is the contribution. The baseline resets when a
record begins, so no step is charged for the gap before it. And the figure is published with
`yp:energy_sampling_period_s` and `yp:energy_attributable`, so the record states that the
number is real consumption in a real window but **not** an attribution. **Energy belongs at
session granularity**; any per-step energy claim in this literature needs a backend sampling
faster than the steps, and should say what its period was.

### E6 — Instrumentation overhead *(measured, Phase 5)*

Full tables in [`docs/E6_RESULTS.md`](../docs/E6_RESULTS.md), rendered from the results
files rather than transcribed. Specification and scored predictions in
[`docs/E6_OVERHEAD.md`](../docs/E6_OVERHEAD.md).

**The central result, and it is the one that was predicted.** Recording a
`yp:justification` costs **nothing this machine can resolve** — over 40 interleaved
rounds of 1,000 calls, the paired difference is 26 ns against a round-to-round
spread of ±352 ns — and **278 bytes, 21.7% of a record**. The trade is *storage for explainability, not speed
for explainability*. That is a far more defensible claim than "it is free", and it is what
the data shows. It also survived being made harder: Phase 1 rewrote the justifications so
they state the result of real checks rather than restating their own instruction
([`PLAN.md`](../PLAN.md) R1), so this is no longer a measurement of f-string concatenation.

**For every agent that does real work, the overhead is not resolvable at all.** At 30
repetitions, interleaved, CA1, CA2, CA3 and CAx each sit inside their own run-to-run
variance — the difference between running them with and without provenance is smaller than
the difference between two runs of either. The margins are 0.5× to 2.9× of the sample
dispersion, against a **3× threshold** required before a figure is printed as a result.

That is the headline, and it is better than a percentage: **the instrumentation is cheaper
than the noise floor of the work it instruments.**

**Overhead is resolvable only for the two agents whose own work is trivial** — and there it
is large, which is why it should be led with:

| | MC1 Compliance, the worst case in the system |
|---|--:|
| the agent's own work | 96 µs |
| …plus building a complete typed PROV record | **+42 µs** |
| …plus writing it to disk | **+1,532 µs** |
| total overhead | **+1,645%** (margin 8.2×) |

A paper that leads with its own worst case is worth more than one that leads with its best
— but report it with the decomposition, or it is unactionable. Explicit instrumentation is
not expensive to *compute*; persisting its output is, and that is a deployment decision.
`TRANSIENT` mode makes it: **−91% of the time cost** for an identical record. `METADATA`
makes the other one: **−37.6% of the bytes**, with every justification retained.

**The resolvability criterion was corrected during this work, and it changed two rows.** It
began as *larger than the noise*, which treats any consistent bias as a finding; a loaded
machine supplies plenty. CA3 and CAx had been reported at +44% and +37% on margins of 2.9×.
The project's own guard test is what caught it — on a shared CI runner, timing the **same
function twice** produced a 147.5 ns difference against 61.0 ns of dispersion and called it
real. The fix was to counterbalance the pair order, so a fixed-order bias cancels instead of
accumulating, and to require a 3× margin. **Write the guard test that fails when your
harness reports noise as a result**; this one earned its place.

**The cost is linear, and was not when first measured.** The scaling sweep fitted an
exponent of **1.468** on building a record, and a 10,000-activity record took 1.72 s. The
cause was a duplicate check on declared derivations that scanned a list. With an O(1)
membership set: **131 ms, exponent 1.066**. Memory is linear too, ~1.3 KiB per
activity, and
held until emission — a real constraint for a long-lived agent, and one for §8.

**The surprising per-call result is that the timestamp dominates.** A tracked step is
~4.5 µs, 64% of it `now_iso()`, and 3× more of that is `.isoformat()` than
reading the clock. The dominant per-step cost of this library is rendering an instant as text — a
property of what PROV stores, not of how it is built. For anyone else implementing a
provenance library this is the most transferable number in the study.

**Which figures transfer.** Run twice on separate occasions: absolute timings moved by up
to 26%, byte counts were **identical**, fitted exponents agreed to within 3%, and the
resolvability verdicts were unchanged for every agent. A third run taken while the machine
was loaded by this study's own earlier levels inflated every absolute figure by about 3×
and changed **no verdict** — which is the strongest available evidence that the margin
criterion, not the clock, is what makes these numbers safe to read. Quote the bytes, the
complexity class and the verdicts; quote the timings as orders of magnitude. Quote the bytes and the complexity class; quote the timings as
orders of magnitude.

**Two library defects were found by this study and fixed before the paper.** An uncached
metadata lookup making `to_prov_json()` 306× slower than it needed to be, and the quadratic
derivation check above. Neither is a result about provenance; both are the argument for
measuring before publishing a performance claim. State them — a reviewer who finds a
performance bug in a paper's artifact trusts nothing else in it, and a paper that found its
own is in a different position.

**Confounds, stated plainly.** The pipeline-level figure (E6e) is **inside the noise**,
dominated by a fixed persist window and process start-up; it is also sequential and
single-process, so it is not a throughput measurement ([`PLAN.md`](../PLAN.md) R8). CA2's
own work is matplotlib rendering, three orders of magnitude larger than its instrumentation,
so its overhead is unresolvable — reported as such rather than as the 5% *speed-up* an
earlier version of the harness produced. Condition A is indistinguishable from OFF at
agent level: the callback layer is cheap, and what it cannot do is not a matter of cost.

## Qualitative results worth a paragraph each

**The same decision, under both instrumentation strategies.** `experiments/fault-escalate`
runs CA1 with no consumers and a 3-second timeout, with the callback baseline attached. A
recovers one fact about the decision — that the verdict was `ESCALATE`, scraped out of the
node's label. B records why: the trigger (`timeout`), the quorum (0 of 3 acknowledged), the
reason (`consumption-unconfirmed`), and the prose that assembles them, down to the integrity
check that *passed* and the choice to archive anyway rather than lose the record. CA1
escalates for two independent reasons that call for opposite responses, and A cannot tell
which one fired — so it cannot distinguish "storage is corrupting records" from "ca3 is not
running". **This is the paragraph to put next to E3's table**: the structural comparison
says the rationale is absent, and this says what being absent costs.

**CA3 locates where a run spent its time, from provenance alone.** In `example_2` the gap
before `CrossEntropyLoss/Training` is 102.870s — 91.4% of the run's 112.530s wall clock; in
`example_0` the gap before `Training` is 64.7% of a 7.810s run. Reaching this took fixing a
check that could never fire: a 3σ rule needs at least 11 samples, because the largest
attainable z-score over *n* samples is (n−1)/√n, and every graph here has fewer. **The
negative result is worth stating** — an unreachable invariant always passes, which is the
most dangerous failure mode a check has, and it is invisible without analysis of this kind.

**CA3 finds real completeness gaps in yProv4ML's own output:** 8 of 9 activities declare a
start time with no end time, and entity typing coverage is 82.1%. Report these as
*completeness* findings rather than anomalies — they describe what the producer recorded,
not how the run behaved, and folding them together made ANOMALY the verdict for essentially
every real graph.

**The same code, two records, two different decisions.** CA1's justification genuinely
differs by what happened:

> `example_0` — ESCALATE, via timeout, 2 of 3 acknowledged: *"Persisted WITHOUT confirmed
> consumption … the persist-after-consume ordering was not satisfied."*
>
> `example_2` — ACCEPT, via quorum, 3 of 3: *"Persisted at quorum … acknowledged by
> [ca2, ca3, cax], the full set required."*

**This is the paper's best evidence for C1** and should be §7's worked example. No callback
could produce either sentence: which branch was taken is a local fact at the moment of
decision, and the distinction only exists because the agent was asked to record it.

**CA2 reports a degraded result that was previously invisible.** Neither bundled yProv4ML
record carries numeric `prov:value` entities, so no measurement can be plotted and CA2 falls
back to graph composition. It now says so (`REVISE`). A chart of graph composition describes
the provenance record rather than the run it documents — a distinction a reader of the old
record could not have made.

## Discussion & limitations — §8 material

Say these; each is defensible, and several are stronger stated than omitted.

**Scope of reflexivity.** The governance layer observes and judges the operational layer but
is not itself consumed: `governance.*` is terminal. Self-application is demonstrated as a
property (MC1 passes MC1 and MC3) rather than as a running loop.

**Fabricated lineage, and why it is worth disclosing.** The tracker previously asserted
derivation from registration order and informed-by from recording order, producing exactly
n−1 edges for n items regardless of what the agent did. The relations were corrected to
declared-or-derived. The methodological point generalises: **a provenance system can
over-report as easily as under-report, and relation counts are the easiest place for it to
happen unnoticed.** Disclosing this strengthens the paper, because the correction is what
makes the remaining counts trustworthy.

**LLM reproducibility.** The record does not yet carry the model identity, sampling
parameters, or prompt hash, so an LLM-bearing step is not reproducible from its own
provenance. `yp:summary_mode` distinguishes a model-backed run from a deterministic one —
previously the two were indistinguishable, justification text included — but that is a
floor, not the goal. Phase 4.

**Content-addressed identifiers are mock handles.** The `21.T11999` prefix is not registered
to this project and nothing resolves it globally. Identical payloads also collapse to one
identifier, so the PID identifies content rather than a storage event.

**Scale.** Two provenance records from one producer family; 24 emitted documents. Nothing in
the agents is ML-specific, but yProv4WFs is untested here.

**Transport.** Single broker, NATS core, at-most-once delivery with no JetStream — a
provenance bus that can drop a record deserves an explicit sentence. The in-process runner
delivers handlers inline, so it exercises none of the distributed path's concurrency; it is
used for isolation in measurement, not as evidence of throughput.

**A4 is resolved, by deciding the claim rather than the code.** Reflexivity in a run is

before Phase 1. A bounded second level with the depth carried in the subject is a plausible
extension and is named as future work, not claimed.
